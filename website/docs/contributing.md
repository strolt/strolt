# Contributing

Contribution guidance is maintained here for the project's documentation website.

## Generating the UI API client

Run `pnpm generate` from the repository root to generate the source schemas before refreshing the UI client. The task invokes the Datamitsu-managed OpenAPI Generator (which manages its Java runtime) and applies `scripts/fix-generated-api.mjs` so Axios type exports remain type-only. Do not install a separate Java runtime or edit `src/api/generated` by hand.

## Building the documentation website

From the repository root, run `pnpm generate` before `pnpm --filter website build`. The explicit generation command refreshes the three generated API schemas, Go SDKs, and manager UI API client. The website build writes the static site under `website/build`; it does not deploy the site. CI runs this same build so dependency and bundler compatibility failures cannot remain hidden behind a successful lint.

The root version-scoped package extensions repair missing runtime dependency declarations in the pinned documentation packages. The scoped WebpackBar override keeps its progress-plugin implementation compatible with the current Webpack API. Preserve pnpm's existing dependency isolation instead of relying on global hoisting or disabling validation.

## Local e2e filesystem and networking

Root `pnpm test` runs all Go module tests and release lifecycle regression tests; it excludes end-to-end tests. Run `pnpm build:docker` to build the three local development images.

Run the complete suite with `pnpm test:e2e` on a Linux filesystem with working file-flag semantics. Some Docker Desktop host bind backends accept `O_NOATIME` but return `EIO` on subsequent reads. In that situation, use a Linux runner or Docker-native Linux volume; do not ignore restic's failed-backup status, weaken integrity assertions, or accept a partial snapshot.

For a containerized runner, the workspace must be visible at the same absolute path to the runner and the Docker daemon so fixture bind mounts resolve correctly. Host-side fixture connections use the runtime's resolved host and mapped port, not a hardcoded loopback address. This preserves ordinary native CI behavior and supports a non-local Docker host without changing the fixtures or assertions.

## Container release lifecycle

`.github/workflows/release.yml` is the release entrypoint and must exist on the default branch for GitHub to offer manual runs. Manual runs default to `verify`; `prerelease` publishes to the `preview` channel, while `unstable` builds a separately selected product ref and publishes to the `unstable` channel. Tags matching `vMAJOR.MINOR.PATCH` publish stable images; SemVer prerelease tags (for example `v1.2.3-rc.1`) publish to `preview`. Registry image tags retain the existing `v` prefix from Git tags. Invalid `v*` tags fail validation before publication. Every push tag eligible to publish must point to a commit reachable from `main`, and its workflow-code SHA must also be in `main` history. Publisher dispatches must select `main` (or an approved `v*` tag on `main`), and the `release` environment must allow `main` and `v*`; do not allow unmerged feature refs there. In `unstable` mode, the separate `product_ref` input may select unmerged product source; the workflow and dispatch SHAs remain bound to approved `main` history, and no code from the selected product ref runs in the publisher.

The workflow persists the dispatch SHA, trusted workflow SHA, selected product ref and resolved product SHA, preparation identity, tool checksums, and resolved base-image/BuildKit/QEMU digests. Verify and preview source SHA equals the dispatch SHA; unstable source SHA is resolved once from `product_ref` and must remain unchanged on reruns. All nine platform producers and the publisher use that same persisted product SHA. Manual identities use `0.0.0-preview.<run_id>.<run_attempt>` for preview and `0.0.0-unstable.<run_id>.<run_attempt>` for unstable; rerunning the same graph reuses its original identity. SDK generation, lint, release regression tests, Go tests, documentation build, manager UI build, and e2e must pass before preparation continues.

The validation job runs pinned GoReleaser `v2.20.3` against `apps/strolt/.goreleaser.yaml`, `apps/stroltp/.goreleaser.yaml`, and `apps/stroltm/.goreleaser.yaml`. It checks each config and builds all three Linux targets for each product with `goreleaser build --snapshot --clean`; GoReleaser is used only as a compiler and never publishes a GitHub release. The workflow installs GoReleaser with Go `1.27.4`, then restores Go `1.27.3` with `GOTOOLCHAIN=local` before building product binaries; `ci-build-strolt.yml` and `ci-e2e.yml` use the same split. The manager UI is built and copied into its Go embed path first. The workflow smoke-tests all nine executables (`--help`, plus Strolt's embedded `version`) before sealing their bundle.

The sealed binary bundle binds the source/version identity, GoReleaser executable hash, each config and artifact-metadata hash, and a SHA-256 checksum for every product/platform binary. Retries restore that exact bundle; if an upload started and its artifact is now missing, the workflow refuses to rebuild it. Before images are built, the input seal also binds the GoReleaser Actions artifact ID/archive digest and manifest SHA; every build, retry, and commit verifies those same values. The release build matrix stages one verified bundle binary at the Dockerfile's `dist/<product>-linux-<arch>/<product>` copy path. Each final image is built offline with `--network=none`, then its extracted executable hash is compared with the sealed binary. Before E2E, the Docker archive's runtime configuration fields and filesystem layer IDs are matched to the OCI image artifact that will be published. After upload and anchoring, a separate read-only `e2e` job restores the `strolt/linux/amd64` piece by its pinned artifact ID/digest, verifies it against the frozen input manifest and GoReleaser binary, and runs E2E with the immutable image ID. The job has no registry-write credential, and `commit-preparation` waits for E2E and all producer receipts. The daemon fixture inherits the Dockerfile's default command and checks both HTTP readiness and Docker health. Each matrix producer seals a receipt binding its OCI artifact ID/digest, record SHA, descriptor, and binary hash. A trusted post-upload step logs the original ID/digest for each image and receipt; reruns fail closed if that anchor is missing or differs. The preparation commit requires all receipts. The per-ref workflow and repository-wide publisher groups both use `cancel-in-progress: false` and `queue: max`; GitHub retains up to 100 pending runs per group and cancels new arrivals when full.

The only frozen Docker input per product/platform is its network-dependent `base` runtime stage. GoReleaser builds the application binaries in the validation job, and the manager UI is embedded before that build. Final images use `--network=none` and digest-identified local OCI base contexts; retries reuse those original snapshots and the sealed binary bundle. When `STROLT_BINARY_ARTIFACT` is set, root `pnpm build:docker` stages the matching sealed binary for each product; otherwise the package tasks build local development binaries.

Alpine base references in the Dockerfiles include both the readable version tag and an immutable multi-platform index digest. Update the digest explicitly when updating Alpine; retain support for all three release platforms. This pins the base image, not packages downloaded later from APK repositories; release dependency snapshots freeze those installed inputs.

Preparation checks all nine final platform images and persists the exact three multi-platform index files and their hashes before any registry writes. Verify follows this complete path without registry credentials. The publisher copies the checked index bytes instead of rebuilding or reserializing them. Actions artifacts are retained for 90 days, subject to repository retention limits. Missing, expired, replaced, mixed, or changed evidence blocks recovery; all-attempt job history and first-upload ID/digest logs prevent checked outputs from being silently replaced or regenerated. Keep the checkpoint step names and the release helper's historical-stage contract aligned.

GHCR and Docker Hub writes are non-atomic. After a partial failure, rerun the original workflow run so completed images are digest-checked and skipped. Never dispatch a replacement version or delete/recreate immutable tags to force recovery. Registry authentication, remote acceptance, and channel promotion are not proved by Verify.

Stable and prerelease images for `strolt`, `stroltm`, and `stroltp` publish to both GHCR and Docker Hub for `linux/amd64`, `linux/arm/v7`, and `linux/arm64`. Stable versions update `latest`; pushed SemVer prereleases and manual `prerelease` runs update `preview`. Manual `unstable` runs publish only to GHCR, under separate `ghcr.io/strolt/<product>-unstable` packages; the versioned run tag and `unstable` alias never touch stable packages or Docker Hub. A channel with no preparation provenance is not overwritten automatically. Concurrent publication is serialized, and promotion compares the numeric preparation `(run_id, attempt)` labels embedded in the image before moving a channel.

Local `pnpm build:docker` tasks use the same GoReleaser configs to create product binaries before Docker builds; `pnpm test:e2e` uses that path for Strolt, and the manager task also builds and embeds its UI. Install with `go install github.com/goreleaser/goreleaser/v2@v2.20.3` and ensure its install directory (`GOBIN`, or `$(go env GOPATH)/bin` when unset) is on `PATH`. The Dockerfiles consume the staged executable only; they no longer compile Go code.

The `release` environment is the publisher boundary and must allow only approved refs (`main` and `v*` tags for this workflow). Independent approval, self-review prevention, and disabled administrator bypass are the recommended controls; this solo-maintainer repository intentionally permits self-review and administrator bypass by owner decision, so approval is not independent. Store `DOCKER_HUB_TOKEN` as an environment secret, not a repository secret. GHCR uses that job's `GITHUB_TOKEN` and `packages: write`. Protect `v*` tags with two rulesets: one with `Restrict creations` and only the release-maintainer bypass (leave deletion unrestricted there); a second with `Restrict updates` and `Restrict deletions` and no bypass. These rulesets govern who can create or mutate tags; the workflow separately checks push-tag and publisher-workflow commits against approved `main` history. Stable, preview, and unstable promotions share the workflow's single serialized publisher group.
